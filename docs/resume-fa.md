# APIForge — رزومه و مصاحبه

> راهنمای کوتاه برای معرفی این پروژه در رزومه و مصاحبه.
> همه‌ی ادعاهای زیر با چیزی که واقعاً پیاده‌سازی و تست شده مطابقت دارد.

---

## ۱. متن آماده‌ی رزومه (فارسی)

### نسخه‌ی کوتاه (۳ خطی — برای بخش پروژه‌ها)

> **APIForge — پلتفرم مدیریت API** | Django 6، DRF، Channels، React 19، TypeScript، PostgreSQL، Redis، Docker
> طراحی و پیاده‌سازی یک API Gateway کامل با احراز هویت کلید API، محدودسازی نرخ،
> شبیه‌سازی و پروکسی ترافیک، ثبت و تحلیل زنده‌ی درخواست‌ها با WebSocket.
> نوشتن ۹۹ تست (SQLite و PostgreSQL) و پیاده‌سازی CI با Ruff، pytest، drf-spectacular و
> بیلد و تست دود ایمیج Docker.

### نسخه‌ی کامل (۵ بولت — برای رزومه‌ی ۱-۲ صفحه‌ای)

> **APIForge — پلتفرم مدیریت API** (پروژه‌ی شخصی) · Django 6 + React 19 · TypeScript · Docker
>
> - پیاده‌سازی **API Gateway** با احراز هویت کلید API، محدودسازی نرخ به‌ازای هر کلید
>   (پنجره‌ی ثابت روی Redis)، حالت شبیه‌سازی (mock) و پروکسی به سرویس upstream
> - طراحی سامانه‌ی **کلید API** با ذخیره‌سازی تنها هش SHA-256 (بدون نگهداری متن اصلی)،
>   نمایش یک‌باره‌ی راز، و چرخش/ابطال کلید
> - ساخت داشبورد **تحلیل ترافیک در لحظه** با تجمیع SQL (خلاصه، نمودار زمانی، توزیع
>   وضعیت، پرترافیک‌ترین مسیرها) و استریم زنده‌ی لاگ‌ها با **WebSocket** و
>   Django Channels، به‌همراه صفحه‌بندی مکان‌نما (cursor) برای پایداری هنگام اسکرول
> - تضمین **جداسازی داده‌ی چندمستاجری** در تمام لایه‌ها (تمام querysetها به کاربر
>   محدود شده‌اند) و پاسخ `404` به‌جای `403` برای منابع دیگران، به‌همراه محافظت در
>   برابر SSRF در پروکسی
> - نوشتن **۹۹ تست خودکار** (روی SQLite و PostgreSQL) و پیکربندی CI شامل Ruff،
>   بررسی Django، تولید اسکیمای OpenAPI، تست مهاجرت‌ها، بیلد فرانت و **بیلد و تست دود
>   ایمیج Docker**؛ خروجی نهایی یک ایمیج چندمرحله‌ای است که فرانت و بک‌اند، API،
>   گیت‌وی و وب‌سوکت را روی **یک پورت** سرو می‌کند

## ۲. متن آماده‌ی رزومه (انگلیسی)

> **APIForge — API Management Platform** (personal project) · Django 6, DRF, Channels,
> React 19, TypeScript, PostgreSQL, Docker
>
> - Built an **API gateway** with API-key authentication, per-key fixed-window rate
>   limiting on Redis, response mocking, and upstream proxying with `httpx`.
> - Designed the **API key system**: only SHA-256 digests are persisted (plaintext is
>   revealed once), with rotate/revoke lifecycle and constant-time verification.
> - Shipped a **live traffic dashboard** — SQL aggregations (summary, time series,
>   status distribution, top endpoints) plus a real-time request-log stream over
>   WebSockets (Django Channels), with cursor pagination so the table stays stable
>   while new rows stream in.
> - Enforced **multi-tenant isolation** at every layer and returned `404` instead of
>   `403` for other tenants' resources to avoid existence leaks; added an SSRF guard on
>   proxied upstreams.
> - Wrote **99 automated tests** (green on SQLite and PostgreSQL) and a CI pipeline with
>   Ruff, Django system checks, OpenAPI schema generation, migration checks, a frontend
>   build, and a **Docker image build plus smoke test**; the final multi-stage image
>   serves the SPA, the API, the gateway and the websockets from a **single port**.

## ۳. معرفی شفاهی (برای مصاحبه)

### ۳۰ ثانیه‌ای (elevator pitch)

> «یک پلتفرم مدیریت API ساختم که کارش شبیه Kong و داشبورد Stripe است. شما پروژه‌ت رو
> تعریف می‌کنی، براش کلید API صادر می‌کنی، و کلاینت‌ها با اون کلید به یه مسیر عمومی
> درخواست می‌فرستن. گیت‌وی درخواست رو احراز هویت می‌کنه، محدودیت نرخ اعمال می‌کنه،
> یا یه پاسخ شبیه‌سازی‌شده برمی‌گردونه یا به سرویس واقعی پروکسی می‌کنه — و هر درخواست
> ثبت و به‌صورت زنده توی داشبورد نمایش داده می‌شه.»

### ۲ دقیقه‌ای (اگر خواستن عمیق‌تر توضیح بدی)

۱. **دو کنترل‌پلن جدا:** `/api/*` با JWT برای مدیریت، `/gateway/*` با کلید API برای ترافیک.
   این جدایی باعث می‌شه کلاینت‌های تو به توکن مدیریتی دسترسی نداشته باشن.

۲. **کلیدها هش‌شده ذخیره می‌شن:** فقط SHA-256 توی دیتابیه، متن اصلی یک‌بار نمایش داده
   می‌شه. پیدا کردن کلید با ۱۲ کاراکتر اول و مقایسه‌ی ثابت‌زمان انجام می‌شه.

۳. **محدودیت نرخ روی cache:** شمارنده‌ی پنجره‌ی ثابت، کلیدش با شناسه‌ی کلید API. توی
   production روی Redis، پس بین همه‌ی workerها مشترکه.

۴. **لاگ زنده:** هر لاگ جدید از طریق Channels به گروه کاربر خاصش push می‌شه. فرانت با
   WebSocket وصل می‌مونه و ردیف جدید رو بالای جدول اضافه می‌کنه بدون رفرش.

۵. **جداسازی چندمستاجری:** هیچ کوئری‌ای بدون فیلتر کاربر نیست؛ برای منابع دیگران
   `404` برمی‌گردم نه `403` تا وجودشون لو نره.

۶. **یک ایمیج، یک پورت:** توی کانتینر، Django خودش پوسته‌ی React رو سرو می‌کنه، پس
   یک پروسه‌ی ASGI همه‌چیز رو جواب می‌ده — همون چیزی که PaaSها انتظار دارن.

## ۴. سؤال‌های احتمالی مصحح + جواب

<details>
<summary><b>چرا کلیدها رو هش کردی؟</b></summary>

چون اگر دیتابیس لو بره، کلیدهای زنده هم لو می‌رن. با هش SHA-256 فقط هش ذخیره می‌شه.
برای اینکه بتونم سریع «کلید درست» رو پیدا کنم، ۱۲ کاراکتر اول رو جدا نگه داشتم
(prefix) و با اون کوئری می‌زنم؛ بعد با `hmac.compare_digest` مقایسه‌ی ثابت‌زمان انجام
می‌دم تا timing attack ممکن نباشه.
</details>

<details>
<summary><b>rate limiting رو کجا پیاده کردی؟ چرا نه دیتابیس؟</b></summary>

توی cache، نه دیتابیس. دلیل: مسیر داغ هر درخواست API روی درخواست‌های واقعی مشتری‌هاست و
نوشتن در دیتابیس برای هر درخواست یعنی write amplification. شمارنده‌ی پنجره‌ی ثابت با
کلید `id کلید + شماره‌ی پنجره` ذخیره می‌شه و پنجره از `int(time / 60)` مشتق می‌شه، پس نه
job پاک‌سازی داریم و نه رشد بی‌رویه. اگه Redis نباشه، LocMem کار می‌کنه (فقط تک‌پروسه).
</details>

<details>
<summary><b>چرا cursor pagination برای لاگ؟</b></summary>

چون لاگ به‌صورت پیوسته در حال رشد است. صفحه‌بندی عددی موقع اسکرول کردن ردیف تکراری یا
ج��افتاده تولید می‌کنه، چون صفحه‌ی ۲ وقتی محاسبه می‌شه که ردیف جدید اضافه شده. cursor
روی یک ستون پایدار و ایندکس‌شده (`created_at`) کار می‌کنه و نتیجه‌اش همیشه پایداره.
</details>

<details>
<summary><b>WebSocket رو با چه چیزی احراز هویت می‌کنی؟</b></summary>

مرورگرها روی handshake وب‌سوکت نمی‌تونن هدر بفرستن، پس JWT رو در query string
فرستادم (`?token=...`) و یک middleware نوشتم که اون رو اعتبارسنجی می‌کنه و در
`scope["user"]` می‌گذاره. اگر نامعتبر باشه کانکشن با کد `4401` بسته می‌شه.
</details>

<details>
<summary><b>چرا از UUID به‌جای integer استفاده کردی؟</b></summary>

دو دلیل: یکدستی — همه‌ی مدل‌ها UUID دارن و کلید خارجی‌ها هم UUID‌اند؛ و اینکه شناسه‌ی
کاربر داخل توکن JWT به‌صورت عدد دنباله‌ای لو نمی‌ره. (این تصمیم وسط پروژه گرفته شد چون
مدل کاربر از `AbstractUser` ارث می‌برد و AutoField داشت؛ همون‌جا یک ناهماهنگی واقعی بود.)
</details>

<details>
<summary><b>چطور مطمئنی که یک کاربر نمی‌تونه به داده‌ی کاربر دیگه دسترسی بگیره؟</b></summary>

دو لایه: اول، تمام querysetها در ویوست‌ست‌ها به `request.user` محدود شدن، پس حتی اگر UUID
یک رکورد دیگر رو حدس بزنی، `404` می‌گیری نه داده. دوم، توابع تجمیع آمار هم پارامتر
`owner` اجباری دارن. یک تست هم دارم که با کاربر دوم آمار و لاگ‌های کاربر اول رو
درخواست می‌کنه و انتظار صفر داره — قبلاً همین تست نبود و باگ واقعی نشت داده را پیدا کرد.
</details>

<details>
<summary><b>برای پروکسی upstream چه کار کردی؟</b></summary>

متد، کوئری، body و هدرها رو با `httpx` منتقل می‌کنم (به‌جز هدرهای hop-by-hop) و پاسخ رو
برمی‌گردونم. برای محافظت در برابر SSRF، مقصدهای loopback و شبکه‌ی خصوصی رد می‌شن مگر
اینکه در حالت توسعه صریحاً مجاز شده باشن.
</details>

<details>
<summary><b>چرا یک ایمیج Docker برای فرانت و بک‌اند؟</b></summary>

چون در محیط‌های PaaS معمولاً باید دو سرویس و یک reverse proxy داشته باشی. با یک ایمیج
چندمرحله‌ای، Django خودش پوسته‌ی React را از طریق WhiteNoise سرو می‌کند و هر مسیر
غیر-API به `index.html` می‌رود (با negative lookahead که `/api/*` را دست‌نخورده می‌گذارد).
نتیجه: یک پروسه، یک پورت، و دیپلوی ساده‌تر.
</details>

<details>
<summary><b>اگر بخواهی این را در مقیاس بالا ببری چه می‌کنی؟</b></summary>

سه چیز: (۱) لاگ‌ها را از دیتابیس به یک مسیر داده‌ای مثل ClickHouse یا Timescale منتقل
می‌کنم چون جدول لاگ سریع‌ترین رشد را دارد؛ (۲) تجمیع آمار را به‌جای محاسبه‌ی درخط، از
جدول‌های rollup یا materialized view می‌خوانم؛ (۳) برای rate limit یک الگوریتم
sliding-window یا token bucket دقیق‌تر جایگزین پنجره‌ی ثابت می‌گذارم، چون پنجره‌ی ثابت
اجازه‌ی دو برابر شدن ترافیک در مرز پنجره را می‌دهد.
</details>

<details>
<summary><b>چه چیزهایی را کامل نفهمیدم / نکرده‌ام؟</b></summary>

- احراز هویت دومرحله‌ای و بازیابی رمز عبور پیاده نشده.
- آزمون سرتاسری (end-to-end) با Playwright ندارم؛ تست‌ها در سطح API و مصرف‌کننده‌ی
  وب‌سوکت هستند.
- پایش و متریک (Prometheus/OpenTelemetry) و سیستم هشدار اضافه نشده.
- استقرار روی سرور واقعی هنوز انجام نشده (پلن رایگان ایرانی محدود بود) — ولی بیلد و
  تست دود ایمیج در CI تأیید شده.
</details>
